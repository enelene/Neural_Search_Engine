# Data Quality Fix — Why v1 failed and how v2 fixes it

> Read this together with the screenshots showing MRR@10 = 0.096 (fine-tuned) vs 1.00 (BM25).
> This document explains exactly what went wrong and why the v2 pipeline should fix it.

---

## The smoking gun

After fine-tuning, your BiEncoder went from **MRR@10 = 0.083** (pretrained) to
**MRR@10 = 0.096** (fine-tuned). That's a ~16% relative gain but the absolute
numbers are still terrible — and BM25 hits a perfect 1.00 on every metric.

Two pieces of evidence make the cause obvious:

### Evidence 1 — The BM25 top result for query #1

```
QUERY: "What is the standard notation for the activation function and
        hidden state of intermediate layers in a feedforward network?"

BM25 #1 chunk_0223:
    "templates. So a neural network is like multinomial logistic regression,
     but (a)..."
```

The relevant chunk **starts with the word "templates."** That's not a sentence
— it's the orphan tail of a sentence from the previous chunk. The whole
corpus is full of these because the original chunker
(`src/pipeline.py:preprocess_and_chunk`) slices every 250 words **without
regard for sentence boundaries**:

```python
# The original buggy logic
words = text.split()
for i in range(0, len(words), chunk_size - overlap):
    chunk_content = " ".join(words[i : i + chunk_size])  # ← cuts mid-sentence
```

### Evidence 2 — The training queries are garbage

Your training data was generated by extracting the **first sentence** of each
chunk as a synthetic query (`_extract_first_sentence` in `src/dataset.py`).
But when chunks start mid-sentence, the "first sentence" is also garbage:

| Chunk ID | Extracted "query" |
|---|---|
| chunk_0006 | `Regex Match Example Patterns Matched r"[A-Z]" an upper case letter…` |
| chunk_0223 | `templates. So a neural network is like multinomial logistic regression…` |

These are not questions. They're meaningless fragments. The model trained on
them learned nothing useful.

### Evidence 3 — Your eval queries favor BM25 overwhelmingly

Look at all 10 hand-crafted queries in `data/evaluation_set.csv`:

```
"How does an encoder-decoder model compute the probability of a target text given a source text?"
"How does BERT use the [CLS] token to predict the similarity of two sentences?"
"Why is beam search preferred over greedy search and exhaustive search?"
```

Every query contains **multiple specific technical terms** that appear
verbatim in the target chunk (`encoder-decoder`, `[CLS] token`, `beam search`).
BM25 — which scores documents purely by keyword overlap — can't lose under
these conditions. It hits MRR = 1.00 because each query lifts unique
terminology directly from the answer chunk.

This means **the comparison itself is rigged against the BiEncoder**. Even a
perfectly-trained neural model couldn't *beat* a perfect BM25 score. The best
the BiEncoder can hope for here is to match BM25.

---

## The two-part fix

### Fix 1 — Sentence-aware chunker (`src/chunker_v2.py`)

The new `SentenceAwareChunker`:
1. Splits the cleaned full text into sentences (handling abbreviations like
   "Fig." and "e.g." correctly).
2. Greedily packs sentences into chunks until the word budget is reached.
3. Carries the last N sentences forward as overlap for context continuity.

**Result on the real PDF:** 1410 chunks (up from 999), every single one
starting at a real sentence boundary. The "first-sentence-as-query" trick
would now produce real sentences — but we're going further:

### Fix 2 — LLM-generated queries (`src/query_generator.py`)

Instead of extracting the first sentence as a query, we ask an LLM (Claude or
GPT) to read each chunk and generate **2 natural-language questions** that
the chunk would answer.

Why this is better than first-sentence extraction:
- The query uses **different vocabulary** than the chunk → forces the model
  to learn semantic similarity, not lexical copying.
- The query reads like an **actual question** ("How do bigram language
  models work?") rather than a fragment ("Regex Match Example Patterns…").
- Two queries per chunk = more training signal per chunk.

Three operating modes are available (see notebook 05):
- **API mode (Anthropic)** — fast, ~$0.50 for 1410 chunks
- **API mode (OpenAI)** — fast, ~$0.40
- **Manual mode** — free, writes prompts you paste into Claude.ai / ChatGPT
  in batches of 20 chunks

## The remaining issue — your evaluation set

Even with perfect training data, the BiEncoder cannot beat BM25 on the
current 10 eval queries because **every query lifts vocabulary directly
from its target chunk.** BM25 is mathematically guaranteed to win that
contest.

**To make the comparison fair, add ~10 paraphrase queries** to
`evaluation_set.csv`. Use synonyms and rephrased phrasing. Examples:

| Original-style query (favors BM25) | Paraphrased query (favors BiEncoder) |
|---|---|
| "What is the standard notation for the activation function?" | "How do we mathematically denote hidden-layer math operations?" |
| "How does BERT use the [CLS] token?" | "Why do transformer models prepend a special symbol to each sentence?" |
| "How can we compute the probability of a full sentence using bigram probabilities?" | "When predicting word sequences word-by-word, how do successive predictions combine?" |

Paraphrased queries are **harder for BM25** (it can't find them via keyword
overlap) and **easier for a well-trained BiEncoder** (it understands semantic
meaning). This is the comparison that will produce the BiEncoder-wins-on-some
results your report needs.

Practical rule of thumb: write 5 "BM25-favoring" + 5 "BiEnc-favoring" eval
queries. Then the comparison table will show each system winning where its
strengths lie — that's the textbook finding for your discussion section.

## Why the original pretrained BiEncoder scored R@1 = 0.00

For context: an out-of-the-box DistilBERT (no fine-tuning) hit Recall@1 of
**zero on all 10 queries**. This is the expected behavior — masked language
modeling produces embeddings that cluster by topic and grammar, not by
query-document relevance. The whole reason for contrastive fine-tuning is to
shape the embedding space so that "questions" land near their "answers."
Without that fine-tuning, the embeddings are useless for retrieval.

This is actually *a feature* for your report: it provides the strongest
possible motivation for the fine-tuning step.
